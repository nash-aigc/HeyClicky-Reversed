## 一、核心洞察：对话后台不是本地 AI

**【已确证】** HeyClicky 的对话后台是一个**三明治架构**：

```
用户（语音 / 文字 / 拍照）
   │
   ▼
本地 App（macOS 菜单栏小程序）
   │  ClaudeAPI 代理（本地一个轻量 struct）
   │  POST {userPrompt, images, promptProfile, responseModelSelection}
   ▼
Worker 后端（https://api.heyclicky.com — 不在用户电脑上）
   │  解析请求体 → 注入计费/配额/模型策略 → 再转发
   │  /v2/chat → 上游 OpenRouter
   │  /chat    → 上游 Anthropic Messages API
   ▼
OpenRouter / Anthropic
   │  SSE 流（text_delta …）
   ▼
Worker 原样转发 SSE → 本地 App 逐字渲染
```

三个关键结论：

1. **模型调用不在本地**。App 里没有任何本地模型的推理代码，只有一个负责"把请求转发出去、把 SSE 流接回来"的代理层。
2. **本地 `ClaudeAPI` 是一个代理 struct，不是模型客户端库**。它只有 4 个存储属性——`apiURL`（worker 地址）、`session`（NSURLSession）、`sseFormat`（SSE 解析模式）、`backendDescription`（"Worker /chat upstream Anthropic" 这类人类可读描述），连请求体结构也是配好给 worker 看的。
3. **计费、配额、权限、模型路由全部在 worker 侧**。客户端只负责携带身份（Supabase token）和说明要什么（promptProfile / responseModelSelection），who-may-act、how-much-it-costs 由服务器裁决。这是它能做到"订阅 + 积分 + 配额"这一切上游控制的基础。

## 二、ClaudeAPI：本地 SSE 代理的真相

**【已确证】** 完全恢复的字段布局：

```
ClaudeAPI (class, 4 个存储属性)
  apiURL              URL?        — worker 端点（WorkerBaseURL 即 https://api.heyclicky.com）
  session             NSURLSession — 网络会话
  sseFormat           SSEFormat    — SSE 解析器模式
  backendDescription  String       — 人类可读后端描述，如 "Worker /v2/chat upstream OpenRouter"
```

对应的上游路由字符串就紧挨在 `HeyClicky/ClaudeAPI.swift` 文件名字面量后面（cstring 2907–2915）：

```
HeyClicky/ClaudeAPI.swift
/v2/chat          ← Worker 上游 OpenRouter 的路径
/chat             ← Worker 上游 Anthropic 的路径
Worker /v2/chat upstream OpenRouter
Worker /chat upstream Anthropic
```

**【推断】** 两条路径对应的两种请求模式：
- `/v2/chat`（OpenRouter 路径）：用于走 OpenRouter 的多模型路由，请求体带 `openRouterCustomModel` / `openRouterVerbosity`（见下节 `ClaudeProxyChatRequest`）。
- `/chat`（Anthropic 路径）：直连 Anthropic Messages API。

为什么是"Worker /v2/chat"而不是"App → OpenRouter"？因为：
- App 根本不持有 OpenRouter API key（配置里只有 `OpenAIChatCompletionsURL` / `AnthropicMessagesURL` 两个 URL 常量，没有 key 字段）；
- `/v2/chat` 挂在 `api.heyclicky.com` 域名下，是 worker 的路径，不是 OpenRouter 的路径。**key 在 worker 手上**，这是一个经典的"BFF（Backend-for-Frontend）代理"设计：客户端无密钥、服务器控配额。

## 三、请求体：App 把什么交给 worker

**【已确证】** 完全恢复的请求体结构：

```
ClaudeProxyChatRequest (struct, 7 字段)
  promptProfile             String    — 提示词档案（决定走哪套系统提示词，如 "agent" / "normal"）
  responseModelSelection    String    — 模型选择（如 "lein" 档 / 质量档位）
  userPrompt                String    — 用户本轮的话
  images                    [ClaudeProxyImagePayload] — 附带截图/照片
  openRouterCustomModel     String?   — 走 OpenRouter 时的显式模型覆盖
  openRouterVerbosity       String?   — OpenRouter 日志/输出详细度
  isProviderFallbackRetry   Bool?     — 是否上游失败后的重试尝试

ClaudeProxyImagePayload (struct, 3 字段)
  base64ImageData   String   — 图片内容（base64）
  imageLabel        String   — 图片的语义标签（如 "screenshot" / "photo"）
  imageMediaType    String   — MIME 类型（cstring 中见到 "image/png"）
```

对应的 JSON 键名也逐个在医院化验单一样完整躺在 cstring 里：

```
user_prompt / response_model_selection / prompt_profile
base64_image_data / image_label / image_media_type
open_router_custom_model / open_router_verbosity / is_provider_fallback_retry
```

**【推断】** `promptProfile` 是这套设计里最值得偷师的一点：把"系统提示词"升级为"档案"（profile），由 worker 按档案装配。App 端不用维护任何提示词模板——今天的"agent 档案"、明天的"角色卡档案"都只是 worker 侧多一个 profile 而已，客户端代码零改动。

`isProviderFallbackRetry` 说明打通了"上游挂了自动换个供应商再试一次"的降级链路。

## 四、SSE 流：事件协议

**【已确证】** 完整恢复的事件名集合（cstring 2927–2945）：

```
data: message_start          ← Anthropic 原生事件
data: content_block_start    ← Anthropic 原生事件
data: content_block_delta    ← Anthropic 原生事件
data: text_delta             ← Anthropic 原生事件（正文增量）
data: clicky_tool_start      ← HeyClicky 自定义：工具开始执行
data: clicky_widget          ← HeyClicky 自定义：widget 事件（payload: widget_kind）
data: clicky_error           ← HeyClicky 自定义：worker/上游错误
data: [DONE]                 ← 流结束标记
```

调试日志确认了本地对流的消化方式（cstring 2938–2950）：

```
📥 SSE event:  content_block_delta / text_delta   — 逐段追加到已渲染文本
🔧 HeyClicky tool starting:  tool_name              — clicky_tool_start 的 payload
🎨 HeyClicky widget event:   widget_kind + payload   — clicky_widget 的 payload
⚠️ HeyClicky worker error:   ...                     — clicky_error 的 payload
```

配套的 payload 键名：

```
widget_kind / payload / tool_name / content_block / server_tool_use
```

**【推断】** 事件协议的设计策略：
- **完全兼容 Anthropic 原生 SSE**——`message_start`、`content_block_*`、`text_delta` 直接透传，客户端照搬 Anthropic 的解析习惯即可；
- **自定义事件全部用 `clicky_` 前缀**——避免撞名，且它们穿过后端时对第三方上游是透明字节流（Anthropic/OpenRouter 不认识 `clicky_*` 也无所谓，worker 直接插入事件、客户端通过 `data:` 前缀统一解析）；
- `server_tool_use` 表示工具调用也走 `content_block` 通道——App 把"模型要调用工具"当作一个普通 content block 处理，而不是另搞一套协议。

## 六、计费：Stripe + Supabase + worker 三方捆绑

**【已确证】** `BillingClient` 完整字段：

```
BillingClient (class, 3 字段)
  workerBaseURL       String        — 计费接口挂在 worker 域名下
  supabaseAuthManager SupabaseAuthManager — 借 token
  urlSession          NSURLSession
```

计费端点（都是 worker 的路径，不是 Supabase 的）：
- `/billing/checkout` — 发起 Stripe Checkout 付款页
- `/billing/portal` — 进入订阅管理门户

套餐状态机字符串（cstring 2810–2830）：`free` / `unlimited` / `past_due` / `unpaid`。

Stripe 订阅对象字段（worker 返回的 JSON 模型，cstring 2815–2845）：

```
plan / billing_interval / cancel_at / cancel_at_period_end
product_id / current_period_end / current_period_start
cap / used / window_resets_at / messages / team_name / tier_source
```

注意 `cap / used / window_resets_at / messages` —— 这是**配额模型**：套餐除了"免费/无限"二态，还记录"本轮周期用了多少消息、什么时候重置"。这解释了 worker 为什么要拦一道：**配额判断在服务器做，客户端从不会看到"服务端已拒绝"之前的任何计费中间状态**。

**【推断】** 计费闭环：
```
App 点击"升级"
  → GET/POST /billing/checkout（带 Supabase Bearer）
  → worker 创建 Stripe Checkout Session，返回 URL
  → App 打开系统浏览器付款
  → Stripe webhook 把结果写回 Supabase 的 profiles 表（plan 字段）
  → App 下次拉 /billing/portal 或 worker 校验时看到新 plan，UI 解锁
```

`past_due` 的语义说明他们连"扣款失败"这种状态都覆盖了——扣款失败不停用功能，而是进 `past_due` 状态让用户去 portal 处理。

## 七、实时语音：worker 帮 App "铸造"临时 OpenAI key

这节属于 doc-02 的一部分，因为它是对话后台的另一条并行通道（Push-to-Talk / Always-On voice）。

**【已确证】** 关键端点与字符串：

```
wss://api.openai.com/v1/realtime?model=          ← 真正的音频通道（OpenAI Realtime）
/agent/realtime/session                          ← 向 worker 要临时 session
/agent/realtime/warmup                           ← 预握手
/agent/realtime/turn                             ← 提交一轮转写后的对话
client_secret                                    ← worker 返回值里的临时密钥
evaporation: "ephemeral"（临时）密钥就是为此设计的
```

本地请求体 `RealtimeEphemeralSessionRequest`（struct，4 字段）：

```
RealtimeEphemeralSessionRequest
  voice             String      — 语音（Sol / Terra / Luna / Astra，cstring 中见到）
  speed             Double      — 语速
  promptContext     String?     — 本轮会话的提示词上下文
  clientCapabilities [String]   — 客户端能力声明
```

音频引擎侧：`RealtimeOutputEngineStarter`（class，2 字段）持有 `AVAudioEngine` + `OS_dispatch_queue`，负责把音频输出接进系统扬声器。

**【推断】** 这正是 OpenAI Realtime 官方推荐的 **"ephemeral token" 架构**：
```
App 需要开语音
  → POST /agent/realtime/session（带 Supabase Bearer）
  → worker 用自己的 OpenAI key 向 OpenAI 请求一个临时 Realtime session
  → worker 把 client_secret（临时密钥，5 分钟有效）原样给 App
  → App 用临时密钥直接连 wss://api.openai.com/v1/realtime?model=gpt-4o-realtime-preview
  → 音频不经过 worker，省带宽、低延迟
```
密钥生命周期短（ephemeral）、且由服务端定制 voice / speed / 上下文——把"谁给你配临时钥匙"的权限收回 worker 手里，App 永远拿不到长期 OpenAI key。

## 八、听写：Deepgram 直连（语音转文字底座）

**【已确证】** 端点：

## 关键教训

1. **BFF 代理是"客户端主权"与"服务器税收"之间的甜点**：模型 key 全在 worker，App 只是薄薄的转发层——这让它可以在不改客户端的情况下改模型、上配额、下策略。想自建同类产品，这层代理是必须有的骨架。
2. **SSE 事件协议用"原生事件透传 + 自定义前缀事件"双轨**：透传让开源生态的解析器白嫖，`clicky_` 前缀事件让自家能力（工具、widget、错误）平滑插入，不破坏兼容性。
3. **临时密钥花钱买安全**：Realtime 和 Deepgram 都用"worker 铸造 ephemeral token"而不是下发长期 key，App 泄露也只是一次性门票。
4. **认证、计费、追踪三件事共用一个 token/一组头**：Supabase JWT 同时服务 /auth 和 /billing，X-Clicky-* 头同时服务排障和产品分析——身份是贯穿所有后端通道的唯一主键。
5. **配额判断放服务器，客户端永远不知道"服务端拒绝之前"**：从 `cap/used/window_resets_at` 看，这是他们生意模式的护栏，也是避免客户端缓存/绕过的基本功。
