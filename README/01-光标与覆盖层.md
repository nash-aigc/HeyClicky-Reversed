## 一、核心洞察：光标不是系统光标

**【已确证】** HeyClicky 的蓝色光标**不是** `NSCursor`，也不是任何系统级光标替换。它是一个**全屏透明无边框 `NSPanel`**，每个屏幕一个实例，内部用 SwiftUI 画出一个蓝色三角/指针形状。

这个设计有三个直接推论：
- 光标可以完全自定义形状（三角、标准指针、旋转圈、停止图标、波形、气泡）
- 光标可以附带任意 SwiftUI 视图（标注高亮、引导点击目标、逐字气泡）
- 光标可以同时出现在多个屏幕上，且不受系统光标样式影响

---

## 二、NSPanel 配置（为什么每个属性都必须这样设）

**【已确证】** 每个 `OverlayWindow(screen:)` 实例是一个 `NSPanel`，其关键属性如下：

| 属性 | 值 | 原因 |
|------|----|------|
| `isOpaque` | `false` | 必须透明，否则遮挡桌面 |
| `backgroundColor` | `.clear` | 同上 |
| `ignoresMouseEvents` | `true` | **绝对不能拦截鼠标事件**，否则用户所有点击都被吞掉 |
| `level` | 极高值 | 浮在所有普通窗口之上 |
| `collectionBehavior` | 跨 Space（`canJoinAllSpaces` / `fullScreenAuxiliary`） | 切桌面时光标必须仍在 |
| `canBecomeKey` | `false` | 不能抢焦点（不会弹到前台） |
| `NSWindow.sharingType` | 按 bundle id 排除 | 截图时窗口不出现，模型看不到自己 |

**【已确证】** `cursorChromeHiddenFromOwnCapture`（reflstr）确认窗口在自身截图中被排除。

**【推断】** `NSHostingView` 被嵌入该 `NSPanel`，将 SwiftUI 视图渲染为窗口内容。窗口 frame 等于 `NSScreen.frame`（全屏覆盖）。

## 三、坐标换算链（四步，最容易出错的地方）

模型输出 `[POINT:860,50:label]` 后，坐标经过四步换算：

```
① 归一化坐标 (0–1000) → 截图像素
   x_pixel = normalized.x / 1000.0 * screenshotWidthInPixels
   y_pixel = normalized.y / 1000.0 * screenshotHeightInPixels
   函数: CompanionManager.screenshotPixelCoordinate(fromNormalizedPoint:...)
   【已确证】符号存在于 by_type

② 截图像素 → 屏幕点 (screen points)
   screenX = pixelX / NSScreen.backingScaleFactor
   screenY = pixelY / NSScreen.backingScaleFactor
   （Retina 屏 scale = 2，所以像素值要除以 2）

③ 屏幕点 → SwiftUI 坐标
   swiftUI.x = screenPoint.x
   swiftUI.y = (screenFrame.origin.y + screenFrame.height) - screenPoint.y
   函数: convertScreenPointToSwiftUICoordinates
   原因: AppKit 原点在左下，SwiftUI 原点在左上
   【已确证】reflstr 中有 convertScreenPointToSwiftUICoordinates

④ 多屏幕选择 (`:screenN` 后缀)
   模型给的坐标附带屏幕编号标签，系统据此将光标定位到正确屏幕
```

**第 ① 步为什么静默失败**：Qwen 视觉模型内部会缩放图片再看，吐出的 `[POINT:x,y]` 是 0-1000 归一化网格。`860` 作为归一化值和作为像素值看起来完全一样——光标只是偏一点，用户会觉得"不太准"但不会认为是 bug。

**【已确证】** reflstr 中有正则 `^\[POINT:\s*`（5386）和 `\[(?:POINT|HIGHLIGHT|SHAPE|TARGET|HOVER):[^\]]*\]`（5371），以及 `^\[POINT:\s*none\s*\]$`（5385）。

## 四、光标状态机与视觉变体

**【已确证】** 从 swift_symbols.json 恢复的完整类型列表：

### 4.1 蓝色光标系（HeyClicky 标志性三角）

| 类型 | 符号 | 用途 |
|------|------|------|
| `BlueCursorView` | `.body`, `.annotationHighlightView(highlightRect:)`, `.guidedClickTargetView(target:)` | 主视图，负责绘制三角 + 高亮标注 + 引导点击目标 |
| `BlueCursorSpinnerView` | `.body` | 录音/处理中的旋转圈 |
| `BlueCursorStopIconView` | `.body` | 停止按钮图标 |
| `BlueCursorWaveformView` | `.body` | 录音波形指示器 |

**【推断】** `BlueCursorView.body` 根据当前状态（idle / navigating / highlighting / guided-click）选择性地显示三角、高亮矩形、或引导点击目标。`annotationHighlightView` 接收一个 `highlightRect:` 参数来绘制元素高亮框。

### 4.2 指针/文字光标系

| 类型 | 用途 |
|------|------|
| `PointerCursorView` | SwiftUI 版标准指针（macOS 箭头形状） |
| `PointerCursorNSView` | NSView 版标准指针（可能用于需要 NSView 能力的场景） |
| `IBeamCursorNSView` | I 形光标（文本输入场景） |

**【推断】** 存在 SwiftUI 和 NSView 两个版本可能是因为：NSView 版可以在 `NSHostingView` 中嵌入时提供更精确的光标热区，或用于某些需要 `NSViewRepresentable` 桥接的场景。

### 4.3 文字气泡（逐字揭示动画）

**【已确证】** 完整恢复的四个相关类型：

| 类型 | 作用 |
|------|------|
| `CursorMessageBubbleView` | 气泡容器，`.body` 负责渲染 |
| `CursorMessageBubbleWordToken` | 单词令牌（逐词出现的最小单位） |
| `CursorMessageBubbleWordRevealModifier` | 逐词揭示修饰符，`.body(content:)` 控制每个 token 的出现时机 |
| `CursorMessageBubbleSizePreferenceKey` | SwiftUI SizePreferenceKey，用于测量气泡尺寸并驱动 reflow |

**【推断】** 逐字揭示动画的实现机制：
1. 流式文本到达后被拆分为 `CursorMessageBubbleWordToken` 数组
2. 每个 token 应用 `CursorMessageBubbleWordRevealModifier`，按时间/流序依次出现
3. 每次新 token 出现时，`CursorMessageBubbleSizePreferenceKey` 向上传递新的尺寸
4. 父视图收到尺寸变化后重新布局，实现自动 reflow

reflstr 中 `_streamedCursorBubbleText`（3815）、`_streamedCursorBubbleOpacity`（3816）、`_showStreamedCursorBubble`（3817）、`streamedCursorBubbleTask`（4001）进一步证实了流式气泡的存在。

## 五、OverlayWindowManager（多屏生命周期）

**【已确证】** `OverlayWindowManager` 恢复了两个嵌套类型：

| 嵌套类型 | 推断用途 |
|----------|---------|
| `OverlayEntry` | 每个屏幕的条目：存储 `NSPanel` 实例 + 对应的 `NSScreen` |
| `ScreenFrameKey` | 字典键类型，用屏幕唯一标识索引各条目 |

**【推断】** 生命周期逻辑：

```
App 启动 / 权限就绪
  → 遍历 NSScreen.screens
  → 每个屏幕创建 OverlayEntry (NSPanel + hostingView)
  → 存入 [ScreenFrameKey: OverlayEntry] 字典

屏幕变化 (NSApplication.didChangeScreenParametersNotification)
  → 移除已消失屏幕的 entry
  → 为新出现的屏幕创建 entry
  → 同步更新所有 entry 的 frame

App 退出
  → 遍历关闭所有 panel
```

reflstr 中 `overlayWindowManager`（3844）确认该类型在运行时被引用。

## 七、屏幕注释层（ScreenAnnotation）

**【已确证】** 完整恢复的类型链：

| 类型 | 嵌套 / 作用 |
|------|-------------|
| `ScreenAnnotationManager` | 管理者，含 `.AnnotationStroke`（笔画）、`.DwellEvent`（悬停事件）、`.StrokeShape`（笔画形状） |
| `ScreenAnnotationOverlay` | 注释覆盖层视图 |
| `ScreenAnnotationPanel` | 独立的注释窗口面板 |
| `ScreenAnnotationCanvasView` | 画布视图，接收绘图输入 |
| `AnnotationShapeOverlayView` | 形状覆盖视图，`.body` 渲染 |
| `AnnotationAccessibilityHarvester` | 辅助功能收割器，含 `.HarvestedElement`（收割到的元素） |

**【推断】** 交互流程：

1. **驻留绘制（Dwell-to-Draw）**：光标在某位置停留超过阈值时触发 `DwellEvent`，开始在该位置绘制注释
2. **笔画系统**：用户绘制的每条线/形状被抽象为 `AnnotationStroke`，其几何形状由 `StrokeShape` 描述
3. **辅助功能收割**：`AnnotationAccessibilityHarvester` 在用户操作时收割当前 UI 的 AX 树元素（`HarvestedElement`），将光标所在位置的元素信息回传给模型

reflstr 中 `element_pointed`（3275）、`rect_area_points`（3364）、`shape_point_count`（3375）进一步证实了注释系统对几何形状和辅助功能元素的处理。

## 九、重构代码草稿（基于已恢复符号的合成推导）

> **注意：以下代码是从恢复的符号名和已知行为推导出的重构草稿，不是逆向得到的原始源码。**

```swift
// 最小版本的 NSPanel 子类（概念模型）
import SwiftUI
import AppKit

/// 每个屏幕一个，负责承载光标的透明窗口
class OverlayWindow: NSPanel {
    init(screen: NSScreen) {
        super.init(
            contentRect: screen.frame,
            styleMask: [.borderless, .nonactivatingPanel],
            backing: .buffered,
            defer: false
        )
        isOpaque = false
        backgroundColor = .clear
        ignoresMouseEvents = true
        level = .screenSaver  // 极高层级
        collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]
        isMovableByWindowBackground = false

        // 截图排除
        // reflstr: cursorChromeHiddenFromOwnCapture
        setContentSize(screen.frame.size)
    }
}

// --- 多屏管理 ---
struct OverlayEntry {
    let panel: OverlayWindow
    let screen: NSScreen
}

class OverlayWindowManager {
    // 嵌套类型: ScreenFrameKey, OverlayEntry
    private var entries: [ScreenFrameKey: OverlayEntry] = [:]

    func createOverlays() {
        for screen in NSScreen.screens {
            let panel = OverlayWindow(screen: screen)
            let entry = OverlayEntry(panel: panel, screen: screen)
            // 用 ScreenFrameKey 索引
            entries[ScreenFrameKey(screen)] = entry
        }
    }

    func syncOnDisplayChange() {
        // 移除已消失的，为新出现的创建
    }
}

// --- 坐标换算链 ---
// ① 归一化 → 像素 (CompanionManager)
func screenshotPixelCoordinate(fromNormalizedPoint point: CGPoint,
                                screenshotWidth: Int,
                                screenshotHeight: Int) -> CGPoint {
    CGPoint(
        x: point.x / 1000.0 * CGFloat(screenshotWidth),
        y: point.y / 1000.0 * CGFloat(screenshotHeight)
    )
}

// ② 像素 → 屏幕点
func screenPoint(fromPixelPoint pixel: CGPoint,
                  backingScale: CGFloat) -> CGPoint {
    CGPoint(x: pixel.x / backingScale,
            y: pixel.y / backingScale)
}

// ③ 屏幕点 → SwiftUI 坐标
func convertScreenPointToSwiftUICoordinates(
    screenPoint: CGPoint,
    screenFrame: NSRect
) -> CGPoint {
    CGPoint(
        x: screenPoint.x,
        y: (screenFrame.origin.y + screenFrame.height) - screenPoint.y
    )
}
```

## 关键教训

1. **归一化坐标是隐形炸弹**：模型输出的 0-1000 值和像素值形态完全一致，漏掉转换不会报错，光标只是偏一点。
2. **窗口常驻优于反复创建/销毁**：`NSHostingView` 重建会丢失状态、产生闪烁，所以用 `@Published var isBuddyShown` 控制可见性，而非窗口显隐。
3. **截图排除是刚需**：如果光标出现在模型看到的截图里，模型会误以为那是 UI 元素并尝试操作它——所以必须按 bundle id 排除。
4. **多屏不能忘 `:screenN`**：没有屏幕编号后缀，光标会指到错误的屏幕，这不是渐进偏差，而是完全错位。
